name: add-slice
description: Adds a use case to a module of this HardSlice solution, a command that changes state, a system command that only the application sends, or a query that only reads, its endpoint protected by an authorization policy when only some callers may call it, by generating its slice and its tests with dotnet new hardslice-command or hardslice-query, and the condition of a job with hardslice-condition, putting its business rule in the aggregate, registering it, filling its logic and its tests, then running the check. Use when asked to add a use case, an endpoint, a command, a job, a query or a feature to an existing module, such as renaming a product or listing the products of a category. # Add a slice

A slice is one use case in `src/MyApp/Features/<Module>/<Slice>/`: its request, its validator, its handler and its endpoint, with its tests at the same path under `tests/`. The templates create them: never write that structure by hand.

Run every command from the root of the solution, the folder of `MyApp.slnx`. If the solution was never built, run `dotnet build` first: the templates read the web project.

## Steps

1. Read the module: its entry in the "Modules and slices" map of `AGENTS.md` and `src/MyApp/Features/<Module>/<Module>Module.cs`. If the module does not exist, use the `add-module` skill; if the aggregate of the use case does not exist, use `add-aggregate`.
2. Read the aggregate the use case creates, changes or reads, in `src/MyApp.Domain/<Module>/`, and its unit tests in `tests/MyApp.Tests/Domain/<Module>/`.
3. Look for the business rule of the use case in the aggregate. If it already owns it, the slice calls that method. If not, add it to the aggregate first: a method that changes its state and throws a `DomainException` when a rule breaks (answered with 400), or a `ConflictException` when the current state forbids it (409), with its unit tests, one per rule. A handler, a validator or an endpoint never holds a business rule.
4. Name the slice after the use case, in PascalCase, verb first, without the `Command` or `Query` suffix: `RenameProduct`, `GetProduct`. Then generate it:
   - the use case changes state: a command, with its validator tests and its integration tests. Add `--parameters none` when it takes nothing from the request (step 6). It returns the `Guid` identifier of the aggregate by default; add `--response none` when it returns nothing (false is answered with 404, refused with `--parameters none`, which has no identifier to look for), or `--response <Dto>` for a DTO of values that the slice declares.

     ```text
     dotnet new hardslice-command --project src/MyApp/MyApp.csproj --module <Module> --name <Slice> --route <route>
     ```

   - the use case is sent by the application only, never by an HTTP request, such as a job or the reaction of a hosted service to an outside event: a system command, with `--endpoint none`. It implements `ISystemCommand<TResponse>`, has no endpoint, and its integration tests send it through `IMediator`. It takes `--parameters` and `--response` as a command does, never `--route` nor `--method`, which are refused.

     ```text
     dotnet new hardslice-command --project src/MyApp/MyApp.csproj --module <Module> --name <Slice> --endpoint none
     ```

   - the use case runs at regular intervals, such as collecting a feed every 30 seconds or purging old rows every night: a recurring system command, with `--every <interval>`, the interval as `[d.]hh:mm:ss`, longer than zero and under 49 days. It implies `--endpoint none` and `--parameters none`, and is refused with `--parameters id` or `--endpoint http`: a new command without parameter is sent at each interval. The template prints its registration, `AddRecurringCommand<TCommand, TResponse>("<Module>:<Slice>", interval)`, whose interval the key `<Module>:<Slice>:Interval` of the configuration replaces, and its integration test runs three cycles on a `FakeTimeProvider`.

     ```text
     dotnet new hardslice-command --project src/MyApp/MyApp.csproj --module <Module> --name <Slice> --every 00:00:30
     ```

   - the use case runs every day at a local time, such as importing a feed every night at 04:30 in Toronto: a scheduled system command, with `--daily-at <hh:mm>` and `--time-zone <id>`, the IANA id of the zone (`UTC` without it). It implies `--endpoint none` and `--parameters none` as `--every` does, and is refused with it. A time that a change of the clocks skips moves forward by the length of the change, such as 02:30 to 03:30, and one that the clocks repeat is sent once. With `--every` or `--daily-at`, `--retry <delay>x<count>` sends the command again after a failed cycle, at most `<count>` times, `<delay>` apart from the failed instant, then the schedule goes on after the last one. A retry that succeeds ends them. With either, `--at-start` also sends the command once when the application starts, before the first instant of its schedule, such as an import that must not wait for the night: the registration chains `AlsoAtStart()` to the schedule, and an integration test runs that cycle at `TestInstants.Start`. The template prints its registration, `AddRecurringCommand<TCommand, TResponse>("<Module>:<Slice>", RecurringSchedule.DailyAt(new TimeOnly(4, 30), "America/Toronto").WithRetries(delay, 3))`, whose keys `DailyAt`, `TimeZone`, `Interval`, `RetryDelay` and `Retries` under `<Module>:<Slice>` of the configuration replace the values, and its integration tests run two days of cycles and, with `--retry`, fail a cycle and each retry with `FailNext`.

     ```text
     dotnet new hardslice-command --project src/MyApp/MyApp.csproj --module <Module> --name <Slice> --daily-at 04:30 --time-zone America/Toronto --retry 01:00:00x3 --at-start
     ```

     A command that its endpoint sends, generated with `--parameters none`, is scheduled too by one more line in `Add<Module>Module`, after its handler, such as `.AddRecurringCommand<ImportScheduleCommand, Guid>("Schedule:ImportSchedule", RecurringSchedule.DailyAt(new TimeOnly(4, 30), "America/Toronto"))`, with `.AlsoAtStart()` after `DailyAt(...)` to send it at start too: its endpoint and its schedule both send it, and its endpoint stays (HS004). An existing command without parameter gets its schedule the same way. No template writes that line: test its cycles with `RecurringCommandCycles` in a test file of its slice, as step 7 says, a cycle at each instant and the cycle at start when it has one.

   - the job must not run in some state, such as a key of the service it reads that is not set, or an import at start that a version already stored makes useless: the condition of its command, a new one or one that exists, scheduled with `--every`, `--daily-at` or the line above. It generates `<Slice>Condition` in the folder of the slice, which implements `IRecurringCommandCondition<<Slice>Command>`, and `<Slice>ConditionTests`, which hold a cycle back with its reason and let one go, and prints the line that registers it after the handler. Add `--response <Dto>` when the command returns a DTO, and `--response none` for a `bool` (a `Guid` by default). It refuses a slice without the file of its command, `<Slice>.cs` or `<Slice>Command.cs`, and a slice that already has its condition.

     ```text
     dotnet new hardslice-condition --project src/MyApp/MyApp.csproj --module <Module> --command <Slice>
     ```

   - the use case only reads: a query of one DTO by its identifier, or of the list with `--result many`, with its integration tests. Its DTO is named after the slice without its verb: `GetScheduledTrips` returns `ScheduledTripsDto`.

     ```text
     dotnet new hardslice-query --project src/MyApp/MyApp.csproj --module <Module> --name <Slice> --aggregate <Aggregate> --route <route>
     ```

   - the use case reads the list that a filter selects, such as the trips of a date: a filtered query, with `--result filtered --parameter <Name>:<Type>`. The filter is read from the query string (`?date=2026-11-04`), and the template adds its validator, the unit tests of that validator and an integration test of the 400 of a request without it. A filter that `--route` names between braces, such as `--route days/{date} --parameter Date:DateOnly`, is read from the route instead, so a request always holds it: its integration test is the one of a value that its binding refuses (400, `/days/not-a-date`), of a value that a route constraint refuses (404, with `{date:datetime}`), or, for a `string`, which binds any text, of a value that its validator refuses, marked `TODO(hardslice):` until the validator has the rule of its format. Any other parameter of the route is refused. The type is one of `string`, `bool`, `int`, `long`, `decimal`, `double`, `Guid`, `DateOnly`, `TimeOnly` and `DateTimeOffset`, written as in C#: for another one, such as an enum of the domain, pass the closest and change it in the query, its validator and its tests.

     ```text
     dotnet new hardslice-query --project src/MyApp/MyApp.csproj --module <Module> --name <Slice> --aggregate <Aggregate> --route <route> --result filtered --parameter Date:DateOnly
     ```

   Always pass `--route` to a slice with an endpoint, the route of the endpoint under the group of the module, named after the resource it creates, changes or reads, never after the use case: `ImportSchedule` posts to `--route versions`, not to `import-schedule`, its default. Use lowercase words separated by hyphens, and route parameters between braces separated by slashes, such as `{productId:guid}/reviews`; `--route /` maps the group itself. A query of one DTO, and a DELETE, append `/{id:guid}`, the identifier they read. Two slices of a module never share a method and a route: read the routes its endpoints already map first. Add `--method` to a command that is not a `POST`: `PUT` when it replaces the resource, `PATCH` when it changes part of it, `DELETE` when it removes it, which reads its `Id` from the route. A query answers `GET` only.

   Add `--require <policy>` to a command or a query whose endpoint only some callers may call, such as an administration endpoint: see [Protected endpoints](#protected-endpoints).

   If the template refuses, read its message, fix the argument and run it again: a refusal prints `created successfully` first, then fails with exit code 105 and creates nothing.
5. Register the slice with the lines the template printed, in `src/MyApp/Features/<Module>/<Module>Module.cs`: the usings the file does not have yet, the registrations by contract in `Add<Module>Module`, and `<Slice>Endpoint.Map(group);` in `Map<Module>Module`, except for a system command, which has no endpoint. A forgotten registration fails `ProgramTests`, which names the type.
6. Fill the logic in `src/MyApp/Features/<Module>/<Slice>/<Slice>.cs`:
   - command: replace the `Id` field with the fields of the use case, except for a `DELETE`, whose endpoint reads it from the route; the validator checks only their shape (required, format, length); the handler injects `AppDbContext`, loads the aggregate with `Set<TAggregate>()` (or adds a new one), calls the method of the aggregate and returns the response. It never calls `SaveChangesAsync`, except to save early as the cases below say: the pipeline saves and commits the transaction. It injects `TimeProvider` when the domain needs the current instant;
   - command without parameters, such as an import that reads its source from the configuration: generated with `--parameters none`, it is an empty record, `public sealed record <Slice>Command : ICommand<TResponse>;`, without validator nor validator tests, and the template prints the registration of its handler alone. Never add a validator to it: an empty one is forbidden. The endpoint reads no body and sends `new <Slice>Command()`, and its integration test posts to its route without a body. A command generated without the option that turns out to take nothing from the request: delete its slice folder and its two test folders, then generate it again with `--parameters none`;
   - system command: a type of its module other than its handler and its validator sends it, or HS004 fails the build, which also refuses an endpoint for it. Background work: a task that a clock triggers, at regular intervals or every day, is a recurring command, generated with `--every` or `--daily-at` and sent by `AddRecurringCommand`, never a hosted service of its own. It sends a new command at each instant of its schedule, the first interval after the start or the next time of day, one cycle at a time, each in a scope of its own and through the whole pipeline, transaction included; it logs a failed cycle, sends it again as `--retry` says, then waits for the next instant, on the `TimeProvider` of the container. A job that must not run in some state, such as a key of the service it reads that is not set, or an import that a version already stored makes useless, gets a condition, which `hardslice-condition` generates as step 4 shows: an `internal sealed` `<Slice>Condition` in the folder of its slice that implements `IRecurringCommandCondition<TCommand>`, registered after its handler with `.AddScoped<IRecurringCommandCondition<TCommand>, <Slice>Condition>()` (`ProgramTests` names a forgotten one). Before each send, in a scope of its own, its `CheckAsync(cycle, cancellationToken)` returns `null` to send the command, or the reason it is not sent: the cycle sends nothing and is not retried, the reason is logged once until it changes, and the schedule goes on. The `RecurringCycle` it receives gives the instant of the cycle, its `Retry` number, and `AtStart` for the cycle at start and its retries. It receives what it reads by its constructor, its options, or the database through `AppDbContext`, and never writes: the work is the command's. A query that loads an entity starts with `AsNoTracking()`, and a read that loads none, such as `AnyAsync`, `CountAsync` or a projection to values, needs none: HS006 reports a write or a tracked read in a condition. Check a setting that the job needs the same way, never with a hosted service that only logs it at start, which the integration tests remove, nor `ValidateOnStart`, which stops the whole application. `AlsoAtStart()` on the `RecurringSchedule`, which `--at-start` chains, or the key `<Module>:<Slice>:AtStart`, also sends the command once when the application starts, under the same conditions, such as an import that must not wait for the night when no version covers the day: its condition holds it back when `cycle.AtStart` and a version covers the day, and lets the nightly cycles go. Any other trigger, such as a queue to consume, is a hosted service: declare it in the folder of the slice it triggers, `src/MyApp/Features/<Module>/<Slice>/`, as an `internal sealed` `BackgroundService` registered with `services.AddHostedService<T>()` in `Add<Module>Module`. It creates the command and sends it through `IMediator` in a scope of its own for each message (`IServiceScopeFactory.CreateAsyncScope()`), never writes itself and reads, if it must, with `AsNoTracking()` on a query that loads an entity, which a read that loads none, such as `AnyAsync`, `CountAsync` or a projection to values, does not need (HS006), catches and logs the exception of a message so that it never stops the application, and injects `TimeProvider` for its timers and delays (HS010 refuses `Task.Delay` and `new PeriodicTimer` without it). Its integration tests keep it with `new AppFactory(database).KeepHostedService<T>()`. A manual trigger over HTTP is another use case: a command slice of its own, with its endpoint;
   - command that creates an aggregate under a unique key, such as one row per trip and service day: declare the unique index in its mapping (`HasIndex(...).IsUnique()`) and its migration, and let the index decide. Two requests that create it at the same time, from the endpoint, a recurring command or a second instance of the application, both pass their reads, then the second commit breaks the index: `TransactionBehavior` turns that unique violation into a `ConflictException`, answered with 409 without the values of the key, as for a duplicate created earlier. Its integration test sends the same creation twice and asserts the 409. When the use case has an exception of its own for the duplicate, the handler saves early and catches the violation (`PostgresException` with `SqlState` `PostgresErrorCodes.UniqueViolation`, inside the `DbUpdateException`) to throw it: the exception of the handler wins. A handler that must read before it creates without ever conflicting, such as one that merges into what a concurrent run created, takes a transaction lock before its read, `await db.Database.ExecuteSqlAsync($"SELECT pg_advisory_xact_lock({LockKey})", cancellationToken);` with a `long` constant of the handler, released by the commit or the rollback of the command. It serializes every run of the command: keep it for a merge that must never fail, as the next item says;
   - commands that run at the same time on the same data, from two requests, a recurring command and its endpoint, or two instances of the application: three cases, each with its own protection. A creation under a unique key relies on the unique index and its 409, as the item above says. A change of a stored aggregate relies on its concurrency token, the shadow property `Version` on `xmin` that `dotnet new hardslice-aggregate` maps: a command that changes an aggregate, through its root or through one of its children only, that another request changed since it loaded it saves nothing, and `TransactionBehavior` answers it with 409, for the caller, or the next cycle of a recurring command, to read the stored state again and retry. Its integration test lets two commands load the same aggregate before either saves, then asserts that one commits and the other throws `ConflictException`, as [Concurrent changes](../add-aggregate/SKILL.md#concurrent-changes) of `add-aggregate` details. A merge that must never fail, such as a collection that enriches what a concurrent run stored and would lose an observation on a 409, takes the transaction lock of the item above before its read. The unique index never protects a change, and the token never protects a creation;
   - command that reads from outside, such as a download or a file: the handler injects what it needs, registered in `Add<Module>Module`, such as `IHttpClientFactory` (`services.AddHttpClient()`) and the options of the module, bound from its section of the configuration. Never a static `HttpClient` nor a path written in the code. An effect it has outside, such as a file it writes, survives a rollback of the command: make it harmless then, such as a file named after the hash of its content, which the next run replaces or reuses. An effect that a rollback must cancel, such as an e-mail, a payment or a message to another system, has no mechanism in this solution yet: stop and tell the user instead of writing it;
   - command that creates or changes a second aggregate of its module, such as the trace of the merge it runs: see [Several aggregates in one command](#several-aggregates-in-one-command). A use case that a second slice runs behind another trigger, such as a job and its administration endpoint: see [One use case behind two triggers](#one-use-case-behind-two-triggers);
   - command that writes many children of one root at once, such as the millions of rows of an import: it saves the root early, then writes the children in bulk through the connection of `AppDbContext`, in the transaction of the command, as [Children written in bulk](../add-aggregate/SKILL.md#children-written-in-bulk) of `add-aggregate` details;
   - query: add the values the use case reads to the DTO and project them in `Select`. Keep `AsNoTracking()` where the generated query starts: a query never loads an aggregate to change it and never saves, and HS006 requires it on each query that loads an entity, while a read that loads none, such as `AnyAsync`, `CountAsync` or a projection to values, needs none. `--aggregate` names the first aggregate it reads: join the others it needs, each with `AsNoTracking()`, and nest DTOs of values for what they hold. A query that reads two modules joins the aggregates of the other module the same way, through `AppDbContext` and in one SQL query, on keys of the same type, and never writes them: their changes go through their own module, as `docs/rules/HS012.md` shows in "Reading the aggregates of another module";
   - filtered query: its endpoint binds the query with `[AsParameters]`, from the query string, where its filter is nullable so that a request without it reaches the validator, which answers 400 naming it, or from the route for a filter that `--route` names, whose generated tests put its value in place of its route parameter (`RouteWith`). Replace the `TODO(hardslice):` marker of its handler with the `Where` of the filter. A second filter is a property of the query, a rule of its validator and its validator test. A query generated without filter that turns out to need one: delete its slice folder and its test folder, then generate it again with `--result filtered`;
   - endpoint: keep the route and the HTTP method that the template mapped, on the group of the module, sending the request through `IMediator` and answering with `TypedResults`. A route parameter of `--route` other than the `{id:guid}` of the template and the filter of a filtered query is yours to bind: add it to the delegate of the endpoint and to the request, and give it a value in `Route` of the generated tests, whose `TODO(hardslice):` marker says so.
7. Replace every `TODO(hardslice):` marker of the slice and of its tests: search for `TODO(hardslice):` under `src/` and `tests/`. The integration tests assert the business outcome, such as the state stored in PostgreSQL, read back from the database, the 400 of an invalid request and the 404 of an unknown identifier; the validator tests assert each refused input. The integration test of a filtered query stores an aggregate that the filter keeps and one it excludes. A system command has no route: its integration tests send it through `IMediator`, and an invalid one throws `ValidationException`. A protected endpoint has a test of its 401, which sends no credentials, and its other tests send the client of its policy, as [Protected endpoints](#protected-endpoints) details. A recurring command is tested through its cycles: `RecurringCommandCycles<TCommand, TResponse>` keeps its service in that test only, waits until the service waits for its next instant, an interval, a time of day or a retry, and moves a `FakeTimeProvider` to it at each `RunNextAsync()`, which returns the response of the cycle or throws its exception. `NextDueAsync()` gives that instant without moving the clock, and `FailNext(count)` fails the next cycles before the pipeline, to test the retries. Its second argument configures the instance that runs the cycles, as `WithWebHostBuilder` would, such as `builder => builder.UseSetting(key, value)` or a fake HTTP handler of a client the command reads. A cycle that a condition holds back throws `HeldCycleException`, whose message is the reason, and with `AlsoAtStart()` the first cycle runs at the start of the application, `TestInstants.Start` unless the third argument of `RecurringCommandCycles`, `start`, gives another instant, such as the evening before in the time zone of a daily schedule: never move `Clock` with `SetUtcNow` before the first cycle. The tests of a condition set up the state in which it holds a cycle back and the one in which it lets it go, in PostgreSQL or on the instance that runs the cycles. Assert what the cycles changed, such as the rows they stored. A command without parameters has no invalid request: its integration tests assert its success, and a failure of the domain when one can happen, such as the 409 of a state that forbids it. An empty test, or one that asserts nothing, does not replace a marker. Data that several slices of the module need follows [Test data shared by the slices of a module](#test-data-shared-by-the-slices-of-a-module), and the tests of a job over every row that matches a rule, such as a purge, [The tests of a job over every row that matches a rule](#the-tests-of-a-job-over-every-row-that-matches-a-rule). The generated tests call the route of the slice under `<Module>Module.Route`, the group of the module.
8. Add the slice to the entry of its module in the "Modules and slices" map of `AGENTS.md`, among its commands or its queries.
9. Run the check, and fix the code until it exits 0. A HardSlice diagnostic names its rule and its sheet in `docs/rules/`: apply the first fix of the sheet that matches.

   ```text
   bash scripts/check.sh     # macOS, Linux, Git Bash
   pwsh scripts/check.ps1    # Windows, PowerShell
   ```

## Several aggregates in one command

A command may create or change several aggregates of its own module in its transaction when they must commit together or not at all, such as the trace of a collection created with the merge it describes: the handler adds or changes each one through `AppDbContext`, and the pipeline saves and commits them together. Each change still goes through a method or a factory of its aggregate.

Prefer a domain event and its reaction when the second change is a consequence that another use case owns, such as a change of another module, or one that the first change does not need to describe itself: the aggregate records the fact, and `add-domain-event` gives the reaction its slice. The reaction still runs in the transaction of the command, before its commit, so its failure rolls the command back too. A change that must be able to fail alone, or happen later, has no mechanism in this solution yet: stop and tell the user instead of writing it with a transaction of its own.

An aggregate of another module is never written by the command, neither added nor changed: its module writes it, through one of its own commands or a reaction to a domain event, as `docs/rules/HS012.md` says.

## One use case behind two triggers

Two slices that run the same use case behind two triggers, such as a system command scheduled every 5 minutes and an administration endpoint that runs it for a given day, never share it through a type of one slice (HS016), nor by sending one request from the other handler through `IMediator`. The shared work goes in a service of the public contract of the module:

- an `internal sealed` class directly in `src/MyApp/Features/<Module>/`, named after the use case, such as `ServiceDayReconciler`, never `Helper` nor `Service`;
- registered by the module in `Add<Module>Module`, as a scoped service (`services.AddScoped<ServiceDayReconciler>()`), and injected into the handler of each slice;
- with a comment that names the slices that use it, so that a change of one of them reads the other.

Each handler keeps what is its own: the request, its validation, its response and the trigger. The service only works inside the transaction of the command that calls it, never calls `SaveChangesAsync` and never sends a request. No rule checks the code of such a service as it checks a handler: read with `AsNoTracking()` on each query that loads an entity you do not change, as in a handler (HS006), read the aggregates of another module as `docs/rules/HS012.md` says, and write only the aggregates of the module, through their methods.

A business rule that both slices apply belongs in the aggregate, not in this service: use `extract-to-domain`.

## Test data shared by the slices of a module

The integration tests of a slice create the rows they need. When several slices of a module need the same data, such as a module that reads the aggregates of two other modules, the code that creates it goes in the test folder of the module, `tests/MyApp.IntegrationTests/Features/<Module>/<Name>Scenario.cs`, named after the situation it builds, such as `ServiceDayScenario`, and each test of those slices calls it. It builds the aggregates of another module through their own factories and methods, such as `ScheduleVersion.Import` or `ObservedTrip.FirstSeen`, never by writing their rows in SQL nor by setting their state, so that their rules hold in the tests too. It stores them through `database.CreateDbContext()`, gives each row a key of its own, such as a new `Guid` or a day that no other test uses, and never relies on rows that another test created.

## The tests of a job over every row that matches a rule

A job that works on every row that matches a rule, rather than on the rows its request names, such as a purge, a retention or a catch-up, also works on the rows that the tests running beside it create in the shared database. Its integration tests each take a database of their own: `await using var isolated = await database.CreateIsolatedAsync();`, then `await using var app = new AppFactory(isolated);`, which `RecurringCommandCycles` takes as any instance for a recurring command, and `isolated.CreateDbContext()` to store the rows and read the outcome. The database is migrated, holds no row of the other tests, and is dropped when the test disposes of it. Never reserve a span of dates or of keys for these tests, nor put them in one class to run them one after the other: the next test written elsewhere breaks that agreement. A job bounded by the instant of its cycle or by its request, such as one that reads the day before and the current day, needs none.

## Protected endpoints

An endpoint that only some callers may call, such as an administration endpoint protected by an API key, requires an authorization policy of the application. The 401 or the 403 of the policy is written by the middleware before the endpoint runs: it is not in the signature of the endpoint, and an integration test of the 401 stands for it, as `docs/rules/HS015.md` says.

1. Choose the policy. The authentication scheme, its options and its policies are cross-cutting: they live in `src/MyApp/Shared/Http/`, registered from `Program.cs` (HS017), never in a module. If the application has no scheme yet, write it there first in standard ASP.NET Core, such as an `AuthenticationHandler<TOptions>` that reads a header, with `AddAuthentication` and `AddAuthorizationBuilder().AddPolicy(...)`, and keep its secret, such as the key, in the configuration (`dotnet user-secrets set` for a local run, never in the code).
2. Choose where the policy goes, as `docs/rules/HS015.md` says: on the group of the module, in `<Module>Module.cs`, when it covers every endpoint of the module, and on the endpoint, in its slice, when it covers some of them only, such as a protected write next to an open read. A `FallbackPolicy` in `Shared/Http` protects every endpoint that does not say `AllowAnonymous`.
3. For a policy on the endpoint, generate the slice with `--require <policy>`, the name of the policy as the application registers it. The endpoint chains `.RequireAuthorization("<policy>")`, the template adds an integration test of the 401 next to the test of the 400, and the other generated tests send their requests through `app.CreateAuthorizedClient("<policy>")`. `--require` writes the name of the policy as a literal, in the endpoint and in the tests: when the application names its policy in a constant, such as `AdminKey.Policy` in `Shared/Http`, replace each literal with that constant, `.RequireAuthorization(AdminKey.Policy)` and `app.CreateAuthorizedClient(AdminKey.Policy)`, with the `using` of its namespace, so that the policy keeps one name. A literal left behind still compiles once the policy is renamed, and fails at the first request of the endpoint. A system command has no endpoint: `--require` is refused with `--endpoint none`, `--every` and `--daily-at`.

   ```text
   dotnet new hardslice-command --project src/MyApp/MyApp.csproj --module <Module> --name <Slice> --route <route> --require <policy>
   ```

4. Give the policy its test client once, in `tests/MyApp.IntegrationTests/AppFactory.cs`, which the application owns: an entry of `AuthorizedClients` named after the policy, that makes a client satisfy it, such as `[AdminKey.Policy] = client => client.DefaultRequestHeaders.Add(AdminKey.Header, AdminApiKey)`, with the test key given to the application in `ConfigureWebHost` by `builder.UseSetting`. Until then, every test that calls `CreateAuthorizedClient` fails with a message that says where to add it. Every protected endpoint of that policy reuses the client, also from an instance derived with `WithWebHostBuilder`: never a client helper per test file.
5. Keep the test of the 401 and complete it if the use case changes state: it sends the request without credentials, or with wrong ones, and asserts that nothing changed. A policy on the group of the module needs the same test for each endpoint it protects, written by hand next to the test of the 400.

When the use case produces a fact that other code reacts to, use the `add-domain-event` skill once the slice passes. A domain event handler without tests (HS014, HS018) is a reaction slice: `add-domain-event` gives it its tests, which handle the event and assert what the handler changed.

## Never

These are the workarounds of [Forbidden](../../../AGENTS.md#forbidden); if the check cannot pass without one, stop and explain the conflict instead.

- Write the files of a slice yourself, or move its tests away from its path.
- Use a type of another slice, make a handler, a validator or an endpoint `public`, or move a type of the slice into the namespace of the module.
- Return an entity from a command, even inside a DTO or a collection.
- Put a business rule in the handler, the validator or the endpoint.
- Leave an empty validator or an empty test, or write a placeholder file, to satisfy a rule.
- Suppress a HardSlice diagnostic, lower its severity or turn the analyzers off.
- Create, edit or delete a protected file: the list of [Forbidden](../../../AGENTS.md#forbidden) names them all.
