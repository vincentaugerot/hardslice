# HS012: a module uses another module only through its public contract

Severity: error. Reported by the architecture tests (`tests/MyApp.ArchitectureTests/ModuleTests.cs`), which fail `dotnet test` and the check scripts.

## Rule

A type of one module never uses a type declared in a slice of another module: not its command, query, DTO, handler, validator or endpoint. Modules talk through the domain, domain events, or the public contract of the other module.

HS016 already forbids a slice from using another slice. HS012 also covers the code of a module that sits outside its slices, such as `<Module>Module.cs` or a mapping, when it reaches into the slices of another module.

An exception type named only in a `catch` clause is a dependency too, including in constructors, async methods and lambdas.

## How modules are identified

The test reads namespaces, which follow the `Features/<Module>/<Slice>/` folders, in the compiled assembly:

| Namespace | Belongs to |
|---|---|
| `MyApp.Features.Bookings` (types declared directly in it) | public contract of module `Bookings`, as HS016 defines it |
| `MyApp.Features.Bookings.CancelBooking` and below | slice `Bookings/CancelBooking` of module `Bookings` |
| `MyApp.Domain.*`, `MyApp.Shared.*`, anything outside `Features` | no module |

## Allowed references

- Any type of the same module, its slices included (HS016 still applies between slices).
- The public contract of another module: types declared directly in `MyApp.Features.<Module>`.
- The domain project: aggregates, value objects, domain events. This includes the aggregates of another module, which a slice reads but never writes: see [Reading the aggregates of another module](#reading-the-aggregates-of-another-module).
- Cross-cutting code in `MyApp.Shared`, framework and third-party types.

## Reading the aggregates of another module

The aggregates of every module live in the domain project, which any module may use, and every module reads and writes the same database through `AppDbContext`. A slice may read the aggregates of another module through `AppDbContext`, in a query that joins them to its own aggregates in SQL: this is the form for a join of thousands of rows, which an abstraction of the public contract would answer by loading both sides in memory. It reads them as it reads its own (HS006 for a query handler, a condition or a hosted service): `AsNoTracking()` on each query that loads an entity, and a projection with `Select` to a DTO of values, never the aggregate of the other module itself.

```csharp
// src/MyApp/Features/Invoicing/GetUnpaidInvoices/GetUnpaidInvoices.cs: a query of module Invoicing that joins its invoices
// to the bookings of module Bookings, in one SQL query.
internal sealed class GetUnpaidInvoicesHandler(AppDbContext db) : IRequestHandler<GetUnpaidInvoicesQuery, IReadOnlyList<UnpaidInvoiceDto>>
{
    public async Task<IReadOnlyList<UnpaidInvoiceDto>> Handle(GetUnpaidInvoicesQuery query, CancellationToken cancellationToken) =>
        await (from invoice in db.Set<Invoice>().AsNoTracking()
               join booking in db.Set<Booking>().AsNoTracking() on invoice.BookingId equals booking.Id
               where invoice.PaidAt == null && booking.Status == BookingStatus.Confirmed
               orderby booking.Period.Start
               select new UnpaidInvoiceDto(invoice.Id.Value, booking.Id.Value, booking.RoomId, booking.Period.Start, invoice.Amount))
            .ToListAsync(cancellationToken);
}
```

Join on keys of the same type: `Invoice` holds the strongly typed `BookingId` of its booking, mapped with the same conversion as `Booking.Id`. EF Core translates no `.Value` of a converted identifier in a join or a filter, so a `Guid` reference compared with `booking.Id.Value` compiles and fails when the query runs. The mapping of the other aggregate stays in its module, in `Features/<Module>/`: the reading module never maps it again.

A slice never writes the aggregates of another module: it never adds, removes nor changes one, through `Add`, `Remove`, `ExecuteUpdate`, `ExecuteDelete` or a method of the aggregate, and never tracks one. A command handler that reads them to decide reads them with `AsNoTracking()` too, so that the transaction of its command saves nothing of the other module. The rules of an aggregate and the domain events it records belong to its module, and a change goes through that module: one of its own commands, or a reaction of that module to a domain event of the module that needs the change (option 2 below). No rule reports such a write: HS012 sees the types a module uses, not what a query does with them.

## Diagnostic

```text
HS012: 'RoomsModule' in module 'Rooms' uses 'BookingDto' from slice 'Bookings/GetBooking' of module 'Bookings'. A module uses another module only through its public contract. Fix: use a type declared directly in namespace 'MyApp.Features.Bookings', react to a domain event, or move the shared rule into the domain. Skill: add-domain-event. Doc: 'docs/rules/HS012.md'.
```

The first symbol is the offending type in your module, the second is the type of the other module it must stop using.

## How to fix

Pick the first option that matches why the other module's type was needed.

1. **A business rule is shared**: move it into the domain, then call the aggregate from both modules.
2. **A module reacts to what another module did**: the aggregate of the first module records a domain event, and the reacting module handles it. The first module does not know who reacts.
3. **A module needs a service of another module, or an isolated piece of its data**: the other module declares an abstraction in its public contract, directly in `Features/<Module>/` with namespace `MyApp.Features.<Module>`, and implements it inside the module.

   ```csharp
   // src/MyApp/Features/Bookings/IRoomBookings.cs: the contract that other modules may use.
   namespace MyApp.Features.Bookings;

   public interface IRoomBookings
   {
       Task<bool> HasConfirmedBookingsAsync(Guid roomId, CancellationToken cancellationToken);
   }
   ```

   The contract exposes what other modules need, not one slice's command, DTO or handler moved there. A query that joins the aggregates of the other module to its own reads them directly instead, as [Reading the aggregates of another module](#reading-the-aggregates-of-another-module) shows: never a contract that returns an `IQueryable` or loads a whole table.

4. **Two modules need a similar request or response shape**: each module declares its own type.

Then run the check script: it must pass with no HS012.

## Skill

The message names the `add-domain-event` skill, in `.claude/skills/` and `.agents/skills/`: it generates a domain event, a record named as a past fact, raises it from the aggregate and adds the reaction slice that handles it, so that a module reacts to another without using its types. For an event that already exists, apply the fix above as its steps do, then run the check script.

## Forbidden workarounds

These mechanisms are not valid fixes for HS012. An exception requires an explicit maintainer decision:

- Moving a slice's command, DTO or handler into the module namespace only to make it reachable from another module.
- Changing a namespace so it no longer matches its `Features/<Module>/<Slice>/` folder, or merging two modules into one to silence the rule.
- Reaching the other module indirectly: reflection, `dynamic`, `Type.GetType` or `Activator.CreateInstance`, resolving its handler from `IServiceProvider` as `object`, or calling its HTTP endpoint from inside the application.
- Sending another module's command through `IMediator` from a module that never names it, with a request built by reflection.
- Deleting, skipping or editing `ModuleTests` or any other test in `tests/MyApp.ArchitectureTests/`.
