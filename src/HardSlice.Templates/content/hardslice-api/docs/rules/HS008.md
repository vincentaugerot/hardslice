# HS008: an aggregate references another aggregate by its identifier

Severity: error. Reported at build time by `HardSlice.Analyzers`, in the `Recommended` and `All` analysis modes. Not reported in test projects.

## Rule

An aggregate is a root that implements `IAggregateRoot` and the child entities, implementing `IEntity`, that it reaches through its members. An aggregate holds the identifier of another aggregate, never the aggregate itself. HS008 reads the type of every instance property and field of an entity, whatever its accessibility, since EF Core maps private fields too. That type contains a root when it is one, or when an element of an array or a type argument contains one: `Room`, `Room?`, `List<Room>`, `IReadOnlyCollection<Room>`, `Room[]`, `(int, Room)`, `Dictionary<int, Room>`.

- A root never contains another root: `Booking.Room` of type `Room : IAggregateRoot`, `List<Room>`, and `Booking.PreviousBooking` of type `Booking` are reported. Another instance of the same type is another aggregate.
- The **possible owners** of a child entity are the roots of the project whose members reach its type, directly or through other child entities: `Booking` owns `BookingLine` when it holds an `IReadOnlyList<BookingLine>`. Two roots can both own a type of child, such as `Note`, each with its own instances.
- A child entity may reference its possible owners, `BookingLine.Booking` for instance, and any child entity. A reference to any other root is reported: `BookingLine.Room`, or `Note.Room` when only `Booking` and `Invoice` reach `Note`.
- Any entity may reference a child entity, and any type that holds no root: `Guid RoomId`, `BookingId`, a value object, an enumeration.

The members inherited from a base class are checked with the entity's generic arguments and possible owners, and reported on its declaration. A diagnostic already reported for the same member and root by a base entity of the same project is not repeated. A base that is an unowned child, or whose open type parameter becomes an aggregate in the derived entity, does not exempt that entity from the check.

The rule asserts nothing when it cannot know the aggregate. A child entity that no root of the project reaches has no known owner, and a root declared in another project may reach the child through private members that are not visible: in both cases, HS008 stays silent.

## Why

An aggregate is the boundary of a transaction: a handler loads one, changes it through its methods and saves it, and its invariants only cover what it contains. A navigation to another aggregate breaks that boundary. A handler that changes a booking can change the room through `booking.Room` in the same transaction, without the methods and the checks of `Room`; EF Core loads, tracks and saves both, the queries load more than the use case needs, and two slices end up locking the same rows for unrelated changes. The aggregates turn into a single graph that every slice must understand.

With an identifier, each aggregate stays small and independent: the handler that needs the room loads it explicitly, by `RoomId`, and the reader of a slice sees which aggregates it touches.

## Diagnostic

```text
HS008: entity 'BookingLine' of aggregate 'Booking' references aggregate 'Room' through property 'Room'. An aggregate references another aggregate only by its identifier. Fix: replace the property with 'RoomId' and load 'Room' in the handler that needs it. Skill: add-aggregate. Doc: 'docs/rules/HS008.md'.
```

The diagnostic is reported on the property, the field or the positional parameter of a record. A member inherited from a base class is reported on the declaration of the entity. The other forms read:

```text
HS008: aggregate 'Booking' references aggregate 'Room' through property 'Room'. ...
HS008: aggregate 'Booking' references another aggregate 'Booking' through property 'PreviousBooking'. ... Fix: replace the property with 'PreviousBookingId' and load 'Booking' in the handler that needs it. ...
HS008: aggregate 'Booking' references aggregate 'Room' through field '_rooms'. ... Fix: replace 'Room' with its identifier in the type of the field and load 'Room' in the handler that needs it. ...
HS008: entity 'Note' of aggregates 'Booking' and 'Invoice' references aggregate 'Room' through property 'Room'. ...
HS008: aggregate 'Booking' references aggregate 'Room' through property 'Room', inherited from 'RoomHolder'. ... Fix: replace the property 'RoomHolder.Room' with 'RoomId' and load 'Room' in the handler that needs it. ...
```

## Bad example

```csharp
// src/MyApp.Domain/Bookings/Booking.cs
public sealed class Booking : IAggregateRoot
{
    private readonly List<BookingLine> _lines = [];

    public Room Room { get; private set; }

    public IReadOnlyList<BookingLine> Lines => _lines;
}

// src/MyApp.Domain/Bookings/BookingLine.cs
public sealed class BookingLine : IEntity
{
    public Room Room { get; private set; }
}
```

## Good example

```csharp
// src/MyApp.Domain/Bookings/Booking.cs
public sealed class Booking : IAggregateRoot
{
    private readonly List<BookingLine> _lines = [];

    public Guid RoomId { get; }

    public IReadOnlyList<BookingLine> Lines => _lines;
}

// src/MyApp.Domain/Bookings/BookingLine.cs
public sealed class BookingLine : IEntity
{
    public Guid RoomId { get; }

    // The way back to its own aggregate is allowed.
    public Booking Booking { get; private set; }
}

// src/MyApp/Features/Bookings/ConfirmBooking/ConfirmBooking.cs
var room = await dbContext.Set<Room>().SingleAsync(room => room.Id == command.RoomId, cancellationToken);
var booking = Booking.Confirm(room.Id, period, existingBookings);
```

## How to fix

1. Replace the reference with the identifier of the aggregate: `Room Room` becomes `Guid RoomId`, or a strongly typed `RoomId`. A collection keeps the identifiers: `List<Room>` becomes `List<Guid>`.
2. When the domain needs data of the other aggregate to decide, the handler loads it and passes what the method needs as parameters, such as the room capacity or the identifier of a confirmed room.
3. When a slice needs to show data of both aggregates, its query handler joins them in a projection to a DTO: the domain does not need the navigation for that.
4. A rule that spans two aggregates, such as "a room is never booked twice for the same period", is checked in a method of one aggregate from data the handler loads, such as the existing bookings of the room, or by a constraint of the database.
5. Map the identifier with EF Core as a plain column, with a foreign key without navigation if you need one: `builder.HasOne<Room>().WithMany().HasForeignKey(booking => booking.RoomId)`.
6. Run the check script again.

## Skill

The message names the `add-aggregate` skill, in `.claude/skills/` and `.agents/skills/`: it generates an aggregate with its identifier, its mapping and its unit tests, and keeps another aggregate by its identifier only. For an aggregate that already exists, apply the fix above as its steps do, then run the check script.

## Forbidden workarounds

These mechanisms are not valid fixes for HS008. Do not use them to make the build pass. An exceptional suppression requires an explicit maintainer decision:

- `#pragma warning disable HS008`, `[SuppressMessage]`, `<NoWarn>`, `<WarningsNotAsErrors>`, `dotnet_diagnostic.HS008.severity` in `.editorconfig` or `.globalconfig`, or a lower `HardSliceAnalysisMode`.
- Typing the reference as `object`, as an interface that `Room` implements without being classified, or as a type parameter: the reference stays and the rule no longer sees it.
- Removing `IAggregateRoot` from the referenced root, or `IEntity` from the child entity, to escape the classification, or changing the contracts of `hardslice.json`.
- Moving the navigation to a base class declared in another project, or the referenced root into another project only to make the reference ambiguous.
- Wrapping the aggregate in a value object or a DTO declared in the domain that holds it as a property: a new type around the same reference.

## What the rule does not detect

- A reference typed `object`, `dynamic`, the `IAggregateRoot` contract itself, a type parameter, or an interface that is not classified as an aggregate root.
- A root held by a member of another type, such as a value object or a DTO that the entity holds: the rule reads the type of the member, its elements and its type arguments, not the members of other types.
- Instances: a reference from a child entity to one of its possible owners can, at run time, designate another aggregate of the same type, and a reference to a child entity of another aggregate of the same type cannot be told from a reference to its own.
- A child entity that no root of the project reaches, and a root declared in another project referenced from a child entity: the owner is unknown, so HS008 asserts nothing.
- A child entity that does not implement `IEntity`, such as an owned type: HardSlice classifies types only by their contracts, and HS902 asks for them on the entities EF Core maps.
- Entities when `hardslice.json`, its `entity` or its `aggregateRoot` contract is unusable: HS900 reports the configuration instead.
- Test projects.
