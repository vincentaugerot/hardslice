# HS001: the domain depends on the base class library only

Severity: error. Reported by the architecture tests (`tests/MyApp.ArchitectureTests/DomainTests.cs`), which fail `dotnet test` and the check scripts.

## Rule

`MyApp.Domain` holds the business rules. It references no other project and no package: no EF Core, no ASP.NET Core, no dependency injection, no HardSlice. Its types use nothing but the base class library.

## How the domain is identified

| Checked | Where |
|---|---|
| Project file | `src/MyApp.Domain/MyApp.Domain.csproj` declares no `FrameworkReference`, `PackageReference`, `ProjectReference` or `Reference`. |
| Compiled assembly | Its assembly references must belong to the base class library, including dependencies introduced by assembly/module attributes or inherited MSBuild references. Every domain type, method bodies and catch clauses included, uses only its own types and those of the base class library (`System.*` assemblies). |

## Allowed references

- Any type of `MyApp.Domain`: aggregates, value objects, domain events, `DomainException`, `ConflictException`.
- The base class library: `System`, `System.Collections.Generic`, `System.Linq`, `System.Text`, and so on.

The first symbol is the domain type, project or assembly at fault, the second is what it must stop using.

## How to fix

Pick the first option that matches why the dependency was added.

1. **Persistence**: map the aggregate with an `internal` `IEntityTypeConfiguration<T>` in `src/MyApp/Features/<Module>/<Aggregate>Configuration.cs`, in fluent API, as `dotnet new hardslice-aggregate` generates it. Never put EF Core attributes, `DbSet` or navigation helpers in the domain; a private parameterless constructor is enough for EF Core.
2. **HTTP or validation**: answers, status codes and input checks belong to the slice (`src/MyApp/Features/<Module>/<Slice>/`). The domain throws a `DomainException`, or a `ConflictException` for a rule broken by the current state, and `Shared/Http` translates it into a 400 or a 409.
3. **A service the rule needs** (a clock, a directory, a price list): the handler gets it from dependency injection and passes the value to the aggregate method.

   ```csharp
   // Before, in the domain: a rule on the current time resolves its clock from the container.
   public void Cancel(IServiceProvider services)
   {
       var now = services.GetRequiredService<TimeProvider>().GetUtcNow();
       // ...
   }

   // After: the domain receives the value and keeps the rule; the handler injects TimeProvider.
   public void Cancel(DateTimeOffset now) { /* ... */ }

   booking.Cancel(clock.GetUtcNow());
   ```

4. **Registration** (`AddXxx` extension methods): it belongs to the module, in `<Module>Module.cs`.

Then run the check script: it must pass with no HS001.

## Skill

The message names the `fix-architecture-violation` skill, in `.claude/skills/` and `.agents/skills/`: it reads the diagnostic and this sheet, applies the first fix above that matches, runs the check script again, and stops to explain the conflict when only a workaround would make it pass.

## Forbidden workarounds

These mechanisms are not valid fixes for HS001. An exception requires an explicit maintainer decision:

- Adding a reference to `MyApp.Domain.csproj`, `Directory.Build.props` or `Directory.Packages.props` that only the domain needs.
- Moving a domain type into `src/MyApp` only to give it access to the infrastructure, while the business rule stays in a handler.
- Reaching the infrastructure indirectly from the domain: reflection, `dynamic`, `Type.GetType`, a static service locator.
- Deleting, skipping or editing `DomainTests` or any other test in `tests/MyApp.ArchitectureTests/`.
