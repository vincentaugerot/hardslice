# HS013: every command with parameters has a validator

Severity: error. Reported by the architecture tests (`tests/MyApp.ArchitectureTests/CommandTests.cs`), which fail `dotnet test` and the check scripts.

## Rule

A command that carries input has a FluentValidation validator, so that a malformed request is answered with 400 naming its fields before its handler runs. `ValidationBehavior` runs every `IValidator<TCommand>` registered for the command.

A command without parameters, such as `record PurgeExpiredBookingsCommand : ICommand<int>`, has no input to check and needs no validator. Queries are out of this rule.

## How commands and validators are identified

The test reads the compiled assembly:

| Element | Identified by |
|---|---|
| Command | a concrete type that implements `ICommand<TResponse>`; an `IQuery<TResponse>` is never a command |
| Parameters | the public instance properties and fields of the command, such as the positional parameters of a record |
| Validator | a concrete type that implements `IValidator<TCommand>`, usually through `AbstractValidator<TCommand>`; its generic arguments and constraints must accept the command |

A validator of `Command<int>` does not validate `Command<string>` or the open `Command<T>`. A generic validator covers an open command only when its constraints accept every construction allowed by that command: a validator restricted to `struct` cannot cover an unconstrained command.

The `unmanaged` constraint is checked explicitly as well: it excludes structs containing references, including nested fields, and cannot cover a command constrained only to `struct`. An open parameter must itself declare `unmanaged`; compatible closed value types are checked through their instance fields.

The test checks that the validator exists. Registering it is the module's job: an integration test that sends an invalid command, required by the slice tests, proves it runs.

## Diagnostic

```text
HS013: command 'ArchiveBookingCommand' in slice 'Bookings/ArchiveBooking' has parameters (BookingId, Reason) but no validator. Every command with parameters has a validator that checks the shape of its input before its handler runs. Fix: declare an internal 'ArchiveBookingValidator : AbstractValidator<ArchiveBookingCommand>' next to the command, register it as 'IValidator<ArchiveBookingCommand>' in its module and test it in 'tests/MyApp.Tests/Features/Bookings/ArchiveBooking/'. Doc: 'docs/rules/HS013.md'.
```

The symbol is the command without validator, followed by the parameters its validator must check.

## How to fix

1. Declare the validator in the slice of the command, `internal`, as `ConfirmBooking` does. It checks the shape of the input only: required fields, formats, lengths. Business rules stay in the aggregate.

   ```csharp
   internal sealed class ArchiveBookingValidator : AbstractValidator<ArchiveBookingCommand>
   {
       public ArchiveBookingValidator()
       {
           RuleFor(command => command.BookingId).NotEmpty();
           RuleFor(command => command.Reason).NotEmpty().MaximumLength(500);
       }
   }
   ```

2. Register it in `<Module>Module.cs` by its contract: `.AddScoped<IValidator<ArchiveBookingCommand>, ArchiveBookingValidator>()`.
3. Test it in `tests/MyApp.Tests/Features/<Module>/<Slice>/`, and add an integration test that sends an invalid command and expects 400 in `tests/MyApp.IntegrationTests/Features/<Module>/<Slice>/`.

Then run the check script: it must pass with no HS013.

## Forbidden workarounds

These mechanisms are not valid fixes for HS013. An exception requires an explicit maintainer decision:

- Turning the command into a query, or implementing `IRequest<T>` directly, to leave the rule's scope while it still changes state.
- Hiding the input from the rule: moving it into an `internal` or `private` member set by the endpoint, a static member, or a service the handler reads.
- An empty validator, or a validator that always succeeds, declared only to satisfy the rule.
- Validating in the endpoint or the handler instead of the validator.
- Deleting, skipping or editing `CommandTests`, `RequestTypes` or any other code in `tests/MyApp.ArchitectureTests/`.
