# HS016: slices never reference each other

Severity: error, set in `.editorconfig`. Reported at build time by `HardSlice.Analyzers`, and by the architecture tests (`tests/MyApp.ArchitectureTests/SliceTests.cs`), which fail `dotnet test` and the check scripts.

## Rule

A type declared in a slice never uses a type declared in another slice: not its handler, command, query, DTO, endpoint, validator, constant, nested type or extension method.

The handlers, domain event handlers, validators and endpoints of a slice are `internal`. Other code reaches a slice only through `IMediator` and its public request, or by raising the domain event a reaction slice handles; the module registers the handlers and maps the endpoint.

## How slices are identified

The analyzer and the architecture tests read namespaces, which follow the `Features/<Module>/<Slice>/` folders:

| Namespace | Belongs to |
|---|---|
| `MyApp.Features.Bookings.CancelBooking` and below | slice `Bookings/CancelBooking` |
| `MyApp.Features.Bookings` (types declared directly in it) | public contract of module `Bookings`, no slice |
| `MyApp.Domain.*`, `MyApp.Shared.*`, anything outside `Features` | no slice |

## Allowed references

- Any type of the same slice.
- The domain project: aggregates, value objects, domain events.
- The public contract of a module: types declared directly in `MyApp.Features.<Module>`, such as a port that several of its slices use.
- Cross-cutting code in `MyApp.Shared`, such as `AppDbContext`.
- Framework and third-party types.
- A type named in a documentation comment, such as `<see cref="..."/>`: the comment documents, it does not depend on the type.

## Diagnostic

```text
HS016: 'CancelBookingHandler' in slice 'Bookings/CancelBooking' uses 'ConfirmBookingHandler' from slice 'Bookings/ConfirmBooking'. Slices never reference each other. Fix: move the shared rule into a domain aggregate, raise a domain event, or use the public contract of module 'Bookings'. Skill: extract-to-domain. Doc: 'docs/rules/HS016.md'.
```

The first symbol is the offending type in your slice, the second is the type it must stop using.

## Architecture test

The analyzer reads the source at build time. `SliceTests` checks the compiled assembly, independently of the analyzer, with the same rule and the same message prefixed `HS016:`. Catch-only references are included, also in constructors, async methods and lambdas. It also checks visibility:

| Role | Identified by | Must be |
|---|---|---|
| Handler | implements `IRequestHandler<TRequest, TResponse>` | `internal` |
| Domain event handler | implements `IDomainEventHandler<TEvent>` | `internal` |
| Validator | implements `IValidator<T>` (FluentValidation) | `internal` |
| Endpoint | a slice type named `<Slice>Endpoint`, or declaring a method that takes an `IEndpointRouteBuilder` such as `RouteGroupBuilder` | `internal` |

```text
HS016: handler 'CancelBookingHandler' in slice 'Bookings/CancelBooking' is accessible outside the assembly. Handlers, domain event handlers, validators and endpoints are internal: other code reaches a slice through IMediator and its public request. Fix: declare 'CancelBookingHandler' internal. Skill: extract-to-domain. Doc: 'docs/rules/HS016.md'.
```

The request and its response DTO stay `public`: they are the slice's API.

Nested `protected` and `protected internal` types are exposed too when their declaring types allow access from another assembly through inheritance. A type inside an `internal`, `private` or `private protected` container remains inaccessible from another assembly.

## How to fix

Pick the first option that matches why the other slice's type was needed.

1. **A business rule is shared**: move the rule into the aggregate, then call the aggregate from both slices. A rule that lives in a handler belongs to that slice only.

   ```csharp
   // Before, in CancelBooking: reuses a check written in ConfirmBooking.
   if (!ConfirmBookingRules.IsActive(booking))
       return false;

   // After: the Booking aggregate owns the rule and enforces it itself.
   booking.Cancel();
   ```

2. **A slice reacts to what another slice did**: the aggregate raises a domain event, and a reaction slice of the reacting module handles it, in the transaction of the command. The first slice does not know who reacts.

   ```csharp
   // src/MyApp.Domain/Bookings/Events/BookingConfirmed.cs: a fact named in the past tense.
   public sealed record BookingConfirmed(BookingId BookingId, Guid RoomId, BookingPeriod Period) : IDomainEvent;

   // In Booking.Confirm: the aggregate records the event, whichever slice confirmed the booking.
   booking._domainEvents.Add(new BookingConfirmed(booking.Id, roomId, period));

   // src/MyApp/Features/Bookings/NotifyOnBookingConfirmed/NotifyOnBookingConfirmed.cs: the reaction, registered by its module.
   internal sealed class NotifyOnBookingConfirmedHandler(AppDbContext db) : IDomainEventHandler<BookingConfirmed> { ... }
   ```

3. **Several slices of a module need the same port or abstraction** (an external service, a read service): declare it in the module public contract, directly in `Features/<Module>/` with namespace `MyApp.Features.<Module>`. The contract holds abstractions shared by the module, not one slice's handler, command or DTO moved there.

   ```csharp
   // src/MyApp/Features/Bookings/IRoomDirectory.cs: used by every Bookings slice that must know a room exists.
   namespace MyApp.Features.Bookings;

   public interface IRoomDirectory
   {
       Task<bool> ExistsAsync(Guid roomId, CancellationToken cancellationToken);
   }
   ```

   Slices do not need such a port to reach an aggregate: they use `AppDbContext.Set<T>()`.

4. **Two slices need a similar request or response shape**: each slice declares its own type. A DTO is part of its slice's API, even when another slice's DTO looks identical.

For a public handler, validator or endpoint, declare it `internal`. If another assembly needs it, it is not the slice's API: send the public request through `IMediator` instead.

Then run `dotnet build` and `dotnet test`: both must pass with no HS016.

## Skill

The message names the `extract-to-domain` skill, in `.claude/skills/` and `.agents/skills/`: it moves the business rule that a slice holds, or that slices share, into the aggregate with its unit test, makes each slice call the method of the domain, then runs the check script.

## Forbidden workarounds

These mechanisms are not valid fixes for HS016. Do not use them to make the build pass. An exceptional suppression requires an explicit maintainer decision and an HS000 justification (`docs/rules/HS000.md`):

- `#pragma warning disable HS016`, or `[SuppressMessage]` / `[SuppressMessage("HardSlice.Architecture", "HS016")]`.
- `dotnet_diagnostic.HS016.severity` in `.editorconfig` or `.globalconfig`, or any other lowered severity.
- `<NoWarn>`, `<WarningsNotAsErrors>`, `<RunAnalyzers>false</RunAnalyzers>` or `<RunAnalyzersDuringBuild>false</RunAnalyzersDuringBuild>` in a project or `Directory.Build.props`.
- Removing, editing or downgrading the HardSlice analyzer, its package reference or its tests, or deleting, skipping or editing `SliceTests` or any other test in `tests/MyApp.ArchitectureTests/`.
- Making a handler, validator or endpoint public, or `InternalsVisibleTo` a production assembly, so that another component calls it directly.
- Moving a slice's handler, command or DTO into the module namespace or `Shared` only to make it reachable from another slice.
- Changing a namespace so it no longer matches its `Features/<Module>/<Slice>/` folder.
- Reaching the other slice indirectly: reflection, `dynamic`, `Type.GetType` or `Activator.CreateInstance`, resolving its handler from `IServiceProvider` as `object`, or calling its HTTP endpoint from inside the application.
- Copying the other slice's business rule into your slice: the rule then exists twice. Move it into the domain instead.
