# HS011: code never blocks on asynchronous work nor declares async void

Severity: error. Reported at build time by `HardSlice.Analyzers`, in every analysis mode, in the domain and the application. Not reported in test projects.

## Rule

Asynchronous work is awaited, all the way up to the endpoint. HS011 reports two faults.

A blocking call, recognized by its symbol in the base class library, never by its name:

| Member | Blocks on |
|---|---|
| `Result` | `Task<TResult>`, `ValueTask<TResult>` |
| `Wait`, every overload, `Task.WaitAll`, `Task.WaitAny` | `Task` and `Task<TResult>` |
| `GetResult()`, called explicitly, as in `GetAwaiter().GetResult()` | `TaskAwaiter`, `TaskAwaiter<TResult>`, `ValueTaskAwaiter`, `ValueTaskAwaiter<TResult>`, and the awaiters of `ConfigureAwait` |

Async void, in every form:

- a method, an override, an interface implementation or a local function declared `async` that returns `void`;
- a lambda or an anonymous method declared `async` and converted to a delegate that returns `void`: `Action`, `Action<T>`, `EventHandler`, `ThreadStart` or a delegate of the application, as in `list.ForEach(async item => ...)`.

## Why

A thread that blocks on a task does nothing until the task completes: under load, requests wait for threads that wait for I/O, and the API stops answering long before the database or the network is busy. Where a synchronization context exists, blocking on a task that needs it never ends. `.Result` and `.Wait()` also wrap any failure in an `AggregateException`.

Nobody can await async void: its caller goes on before the work ends, a test cannot wait for it, and the transaction of a command commits before the work is done. An exception thrown in it reaches no caller: it crashes the process. `list.ForEach(async item => ...)` returns at once, before any item is processed.

## Diagnostic

```text
HS011: 'ConfirmBookingHandler.Handle' blocks on 'Task<TResult>.Result'. Code never blocks on asynchronous work. Fix: make the caller async and await the task. Skill: fix-architecture-violation. Doc: 'docs/rules/HS011.md'.
```

The diagnostic names the member the call is in, or the constructor, the property or the top-level statements, and the blocking member of the base class library. The fix depends on that member: `Task.WaitAll` asks for `Task.WhenAll`, `Task.WaitAny` for `Task.WhenAny`, and `Wait` with a timeout or a token for `WaitAsync`. Async void follows the same shape:

```text
HS011: 'BookingNotifier.Notify' is async void. Asynchronous code returns a task its caller awaits: nobody can await async void, and its exceptions crash the process. Fix: return Task instead of void, and await it where it is called. Skill: fix-architecture-violation. Doc: 'docs/rules/HS011.md'.
HS011: an async lambda of 'BookingNotifier.NotifyAll' is async void: it is converted to 'Action<Booking>', which returns void. ... Fix: replace 'List<T>.ForEach' with a foreach loop that awaits each call. ...
```

## Bad example

```csharp
// src/MyApp/Features/Bookings/ConfirmBooking/ConfirmBooking.cs
public async Task<Guid> Handle(ConfirmBookingCommand command, CancellationToken cancellationToken)
{
    var period = new BookingPeriod(command.Start, command.End);
    var existingBookings = db.Set<Booking>()
        .Where(booking => booking.RoomId == command.RoomId && booking.Status == BookingStatus.Confirmed)
        .ToListAsync(cancellationToken).Result;
    // ...
}

// src/MyApp/Features/Bookings/BookingNotifier.cs
public void NotifyAll(List<Booking> bookings) => bookings.ForEach(async booking => await notifier.Send(booking));
```

## Good example

```csharp
// src/MyApp/Features/Bookings/ConfirmBooking/ConfirmBooking.cs
public async Task<Guid> Handle(ConfirmBookingCommand command, CancellationToken cancellationToken)
{
    var period = new BookingPeriod(command.Start, command.End);
    var existingBookings = await db.Set<Booking>()
        .Where(booking => booking.RoomId == command.RoomId && booking.Status == BookingStatus.Confirmed)
        .ToListAsync(cancellationToken);
    // ...
}

// src/MyApp/Features/Bookings/BookingNotifier.cs
public async Task NotifyAll(List<Booking> bookings, CancellationToken cancellationToken)
{
    foreach (var booking in bookings)
        await notifier.Send(booking, cancellationToken);
}
```

## How to fix

1. A blocking call: make the method that holds it `async`, returning `Task` or `Task<T>`, and `await` the task. Then make its callers async and await it too, up to the handler or the endpoint, which are already asynchronous. Pass the `CancellationToken` along.
2. `Task.WaitAll` and `Task.WaitAny`: `await Task.WhenAll(...)` or `await Task.WhenAny(...)` with the same tasks. `Wait` with a timeout or a token: `await task.WaitAsync(timeout, cancellationToken)`.
3. `.Result` on a task already awaited is reported too: use the value of the `await` instead, or await the task a second time.
4. A constructor, a property or a field initializer cannot await: move the asynchronous work into an async method, such as the handler that uses the value, or a static `CreateAsync` factory.
5. An async void method or local function: return `Task` instead of `void`, and await it where it is called. An override or an interface implementation keeps the signature it implements: change that member to return `Task` when the application declares it, otherwise make the method synchronous.
6. An async lambda given to a delegate that returns `void`: replace `List<T>.ForEach` with a `foreach` loop that awaits each call, give the lambda a delegate type that returns `Task` (`Func<T, Task>`), or, for an event, subscribe a synchronous handler and hand the work to code that awaits it.
7. Run the check script again.

## Skill

The message names the `fix-architecture-violation` skill, in `.claude/skills/` and `.agents/skills/`: it reads the diagnostic and this sheet, applies the first fix above that matches, runs the check script again, and stops to explain the conflict when only a workaround would make it pass.

## Forbidden workarounds

These mechanisms are not valid fixes for HS011. Do not use them to make the build pass. An exceptional suppression requires an explicit maintainer decision:

- `#pragma warning disable HS011`, `[SuppressMessage]`, `<NoWarn>`, `<WarningsNotAsErrors>`, or `dotnet_diagnostic.HS011.severity` in `.editorconfig` or `.globalconfig`.
- Blocking through another member the rule does not list: a `ManualResetEventSlim` or a `SemaphoreSlim.Wait` that waits for the task, a `while (!task.IsCompleted)` loop, `Thread.Sleep`, or a method of a library that blocks for the code.
- Calling the synchronous version of an API only because its async version is awaited, such as `SaveChanges()` instead of `await SaveChangesAsync()`, or `ToList()` instead of `await ToListAsync()`, on a database query.
- Discarding the task instead of awaiting it, as in `_ = SendAsync()`, or calling an async method without `await`, to replace an async void.
- Storing the delegate in a variable, reaching the task through `dynamic` or reflection, or adding an auto-generated header, only to hide it from the rule.

## What the rule does not detect

- Blocking members of other types: `Thread.Sleep`, `SemaphoreSlim.Wait`, `ManualResetEventSlim.Wait`, `Monitor`, the synchronous APIs of EF Core, `HttpClient` or streams, and methods of libraries that block internally.
- A blocking call in a method of another assembly that the code calls: the methods it calls are not followed.
- A task started and never awaited, such as `_ = SendAsync()` or a missing `await`.
- Test projects, where `async void` and blocking calls are a matter for the test framework.
