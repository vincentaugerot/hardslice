# Item templates

`HardSlice.Templates` ships six item templates besides the `hardslice-api` solution template. Each one generates one element of a solution in its place, with its tests, and prints the registrations to add: it never edits an existing file. The skills of the [agent loop](agent-loop.md) call them, so an agent never recreates the structure of an element by hand.

| Template | Generates | Skill that calls it |
|---|---|---|
| [`hardslice-module`](#a-module) | the public contract of a module, which registers and maps its slices | `add-module` |
| [`hardslice-aggregate`](#an-aggregate) | an aggregate root, its identifier, its EF Core mapping and its unit tests | `add-aggregate` |
| [`hardslice-entity`](#a-child-entity) | a child entity of an aggregate, its identifier, its EF Core mapping and its unit tests | `add-aggregate` |
| [`hardslice-command`](#a-command-slice) | a command slice: command, validator, handler, endpoint and tests, or a system command without endpoint | `add-slice` |
| [`hardslice-query`](#a-query-slice) | a query slice that reads an aggregate: query, DTO, handler, endpoint and tests, and the validator of a filter | `add-slice` |
| [`hardslice-event`](#a-domain-event-and-its-reaction) | a domain event and, on request, the reaction slice that handles it, with its tests | `add-domain-event` |

The examples below run from the root of a solution generated as `Rooms` by [Getting started](getting-started.md), once it is restored (after a first build or check). `--project` names the web project: the template reads the name of the application, its `RootNamespace`, and its modules from it.

The generated code always builds without any HardSlice diagnostic, but an element is never generated "done": its tests end with `Assert.Fail("TODO(hardslice): ...")` and `dotnet hardslice check` fails while a `TODO(hardslice):` marker is left, until the business logic and its assertions are written.

## A module

```text
dotnet new hardslice-module --project src/Rooms/Rooms.csproj --name Payments
```

It creates `src/Rooms/Features/Payments/PaymentsModule.cs`, the public contract of the module: `AddPaymentsModule`, which registers its slices, and `MapPaymentsModule`, which maps them on the group `/payments`, the name of the module in kebab-case (`--route` sets another one), held by its constant `Route`. It creates no other file: the folder of its domain, `src/Rooms.Domain/Payments/`, and its test folders, `tests/Rooms.Tests/Domain/Payments/`, `tests/Rooms.Tests/Features/Payments/` and `tests/Rooms.IntegrationTests/Features/Payments/`, appear with the first aggregate, slice or event that the templates below generate in them, so no placeholder file is left behind. Then it prints the using and the two lines to add to `Program.cs`.

The empty module builds and passes the check: no rule asks a module for a slice or a test. Without `--project`, before the first restore, with a name that is not PascalCase or ends with `Module`, or with a route that is not made of lowercase words, it exits with an error and creates nothing. It refuses to overwrite an existing module without `--force`.

## An aggregate

```text
dotnet new hardslice-aggregate --project src/Rooms/Rooms.csproj --module Payments --name Invoice
```

It creates the aggregate root `Invoice` and its identifier `InvoiceId`, a `readonly record struct` that wraps a `Guid Value`, in `src/Rooms.Domain/Payments/`, its EF Core mapping `InvoiceConfiguration` in `src/Rooms/Features/Payments/`, and its unit tests in `tests/Rooms.Tests/Domain/Payments/`. The root is `sealed` and implements `IAggregateRoot`: a private constructor for persistence, a static factory method `Create` to rename after the business fact and give the rules of the aggregate, no public setter, and a private list of events that `DequeueDomainEvents()` returns and empties. The mapping uses the table `Invoices`, the name followed by `s` (`--table` sets another one), converts the identifier and ignores the events. Then it prints the migration to add: there is nothing to register, `AppDbContext` applies the mapping by itself.

Its unit test of the state ends with `TODO(hardslice):`, and the integration tests fail until the migration is added: `MigrationsTests` finds changes missing from the migrations, and once the solution has a migration, EF Core refuses to migrate the database of the others.

It exits with an error and creates nothing without `--project`, before the first restore, with a name or a module that is not PascalCase, for a module without `Features/<Module>/<Module>Module.cs`, with a table that is not made of letters, digits and underscores, or with a name that the generated code could not use: that of a module or a namespace of the application (`Rooms`, `Domain`) or of a type that its files import (`Task`, `File`). It refuses to overwrite an existing aggregate without `--force`.

## A child entity

```text
dotnet new hardslice-entity --project src/Rooms/Rooms.csproj --module Payments --aggregate Invoice --name InvoiceLine
```

It creates the child entity `InvoiceLine` of the aggregate `Invoice` and its identifier `InvoiceLineId` in `src/Rooms.Domain/Payments/`, its EF Core mapping `InvoiceLineConfiguration` next to `InvoiceConfiguration` in `src/Rooms/Features/Payments/`, and its unit tests in `tests/Rooms.Tests/Domain/Payments/`. The child is `sealed` and implements `IEntity`: a private constructor for persistence, a static factory method `Create` to rename after the business fact, and no public setter. The mapping uses the table `InvoiceLines`, the name followed by `s` (`--table` sets another one), and stores the identifier of the root through `InvoiceIdConverter`, a `ValueConverter` of the module that the first child of `Invoice` creates and the next ones reuse. The mapping of the root may use it too, with `HasConversion<InvoiceIdConverter>()`. Then it prints what to complete and the migration to add.

`--link` sets how the child is tied to its root:

- `collection`, by default: the root holds the child in a collection, loaded and saved with it, named as the table. The template prints the private list and its read-only view to add to the root, such as `public IReadOnlyList<InvoiceLine> InvoiceLines => _invoiceLines.AsReadOnly();`, with the methods of the root that add, change and remove a child: it never edits the root. The identifier of the root is a shadow property of the mapping, the child knows nothing of it. A child removed from the collection is deleted. Until the root holds the collection, EF Core cannot build the model, so the integration tests and `dotnet ef` fail.
- `id`: the child holds `InvoiceId InvoiceId`, the identifier of its root, and the root holds nothing of it. This is the form of a collection too large to load with its root, such as millions of rows: a command writes the children of one root apart from it, and a query reads them by the identifier of the root. HS008 knows no owner for such a child and reports nothing, as [its sheet](../src/HardSlice.Templates/content/hardslice-api/docs/rules/HS008.md#large-child-collections) says.

In both forms, a foreign key deletes the children with their root. The unit test of the state ends with `TODO(hardslice):`, and the integration tests fail until the migration is added, as for an aggregate.

It exits with an error and creates nothing without `--project`, before the first restore, with a name, a module or an aggregate that is not PascalCase, for a module without `Features/<Module>/<Module>Module.cs`, for an aggregate without `Features/<Module>/<Aggregate>Configuration.cs`, with a table that is not made of letters, digits and underscores, with a name that the generated code could not use, as for an aggregate, or with a name that the module already maps, that of its aggregate included.

## A command slice

```text
dotnet new hardslice-command --project src/Rooms/Rooms.csproj --module Bookings --name ExtendBooking
```

It creates `src/Rooms/Features/Bookings/ExtendBooking/ExtendBooking.cs`, with the command `ExtendBookingCommand`, its validator, its handler and its endpoint `POST /bookings/extend-booking`, the validator tests in `tests/Rooms.Tests/Features/Bookings/ExtendBooking/` and the integration tests in `tests/Rooms.IntegrationTests/Features/Bookings/ExtendBooking/`. Then it prints the lines to add to `BookingsModule.cs`: the usings, the registrations of the handler and the validator, and the call of `Map`. `--response` sets what the command returns: `id` (a `Guid`) by default, `none` (a `bool` whose `false` is answered with 404), or the name of a DTO of values, which the slice declares.

`--route` sets the route of the endpoint under the group of the module, and `--method` its HTTP method: `POST` by default, `PUT`, `PATCH` or `DELETE`, in any case. Pass `--route` every time, named after the resource rather than the use case: `--name ImportSchedule --route versions` maps `POST /bookings/versions`, where the default, the name of the slice in kebab-case, would put the verb of the use case in the URL. That default never collides with the route of another slice of the module, which a route chosen by hand can: two slices that map the same method and route fail only at run time. A route is made of lowercase words separated by hyphens, and of route parameters between braces such as `{roomId:guid}`, separated by slashes. `--route /` maps the group itself. A `DELETE` has no body: with `--parameters id`, its endpoint reads the `Id` of the command from the route, which `/{id:guid}` follows. The integration tests call the route under `BookingsModule.Route`, the constant of the group, so a module created with its own `--route` needs no change. A route parameter other than that `{id:guid}` is left between braces in `Route`, with a `TODO(hardslice):` marker: give it a value in the tests and bind it in the endpoint.

`--parameters` sets what the command takes from the request: `id` by default, a `Guid Id` to replace with the fields of the use case, checked by its validator. `none` generates a command without parameters, such as an import that reads its source from the configuration: an empty record, an endpoint that reads no body, no validator nor validator tests, and an integration test that posts without body and checks its success instead of a 400. The template then prints the registration of the handler alone. It combines with `--response id` and with a DTO, never with `--response none`, whose 404 answers an unknown aggregate that such a command has no identifier to look for.

`--endpoint` sets how the command is sent: `http` by default, an endpoint of the module. `none` generates a system command, which only the application sends, such as a job or a hosted service that reacts to an outside event: it implements `ISystemCommand<TResponse>`, has no endpoint, and its integration tests send it through `IMediator` in a scope of their own, an invalid one throwing `ValidationException` instead of a 400. The template then prints the registrations without the call of `Map`, and says that HS004 fails the build until a type of the module sends the command, such as a hosted service in the folder of the slice. It combines with `--parameters` and `--response`, never with `--route` nor `--method`, which choose an endpoint.

`--every <interval>` generates a recurring system command, which the application sends at regular intervals, such as `--name CollectRealtimeFeeds --every 00:00:30` for a feed read every 30 seconds. The interval is `[d.]hh:mm:ss`, longer than zero and under 49 days. It implies `--endpoint none` and `--parameters none`: a system command without parameter, without validator nor endpoint. The template prints the registration of its handler and of `services.AddRecurringCommand<TCommand, TResponse>("<Module>:<Name>", interval)`, the service of `Shared/Messaging` that sends a new command one interval after the start, then at each interval, one cycle at a time, each in a scope of its own, on the `TimeProvider` of the container. A failed cycle is logged and the next one runs: the application keeps running. The key `<Module>:<Name>:Interval` of the configuration replaces the interval, and an invalid one stops the start of the application. Its integration test runs three cycles with `RecurringCommandCycles<TCommand, TResponse>`, which keeps the service in that test only, waits until the service waits for its next instant and moves a `FakeTimeProvider` to it: no test waits for the real interval, and no other test starts it. Its second argument configures the instance that runs the cycles, as `WithWebHostBuilder` would, such as a setting or a fake HTTP handler of a client that the command reads. It combines with `--response id` and with a DTO.

`--daily-at <hh:mm>` generates a scheduled system command, which the application sends every day at that local time, in the time zone of `--time-zone <id>`, an IANA id such as `America/Toronto` (`UTC` without it), such as `--name ImportNightlySchedule --daily-at 04:30 --time-zone America/Toronto` for a feed imported every night. A time that a change of the clocks skips moves forward by the length of the change, such as 02:30 to 03:30, and a time that the clocks repeat is sent once, at its first instant. Like `--every`, it implies `--endpoint none` and `--parameters none`. The template prints `services.AddRecurringCommand<TCommand, TResponse>("<Module>:<Name>", RecurringSchedule.DailyAt(new TimeOnly(4, 30), "America/Toronto"))`, whose keys `<Module>:<Name>:DailyAt` and `<Module>:<Name>:TimeZone` of the configuration replace the time and the zone. A zone that the machine does not know stops the start of the application. Its integration test runs two days of cycles and checks the local time of each.

`--retry <delay>x<count>` sends the command of `--every` or `--daily-at` again after a failed cycle, such as `--retry 01:00:00x3` for three retries an hour apart. The delay is `[d.]hh:mm:ss`, longer than zero and under 49 days, and the count goes from 1 to 99. Each retry comes one more delay after the instant of the failed cycle, a retry that succeeds ends them, and the next instant of the schedule comes after the last one. The registration ends with `.WithRetries(delay, count)`, whose keys `<Module>:<Name>:RetryDelay` and `<Module>:<Name>:Retries` replace the values. Its integration test fails the cycle and each retry with `FailNext`, before the pipeline of the command, then checks the instant of each retry and of the next cycle.

The same service sends a command that keeps its endpoint, generated with `--parameters none`: one more line in its module, after its handler, such as `.AddRecurringCommand<ImportScheduleCommand, Guid>("Schedule:ImportSchedule", RecurringSchedule.DailyAt(new TimeOnly(4, 30), "America/Toronto"))`, and both its endpoint and its schedule send it. HS004 still asks for its endpoint, and `RecurringCommandCycles` tests its cycles.

No option generates a condition, which a recurring command needs when it must not run in some state, such as a key that is not set: write `<Slice>Condition`, an `IRecurringCommandCondition<TCommand>`, in the folder of the slice and register it after the handler, as the skill `add-slice` details. `RecurringSchedule.AlsoAtStart()` also sends the command once at start, under the same conditions.

`--require <policy>` protects the endpoint with an authorization policy that the application registers in `Shared/Http` with its authentication scheme, such as `--name ImportSchedule --route versions --parameters none --require AdminKey`. The endpoint chains `.RequireAuthorization("AdminKey")`, an integration test asserts its 401 without authentication, next to the test of the 400, and the other generated tests send their requests through `app.CreateAuthorizedClient("AdminKey")`. That client comes from `AuthorizedClients`, a table of `AppFactory` that the application fills once per policy, such as with a client that sends the test key that `AppFactory` gives the application. A policy without client fails each test that sends it, with a message that says where to add it. The template says so after the registrations. The 401 is not in the signature of the endpoint: the sheet of HS015 says why, and when a policy goes on the group of the module instead. `--require` is refused with `--endpoint none`, `--every` and `--daily-at`, whose system command has no endpoint, and with a name other than letters, digits, `.`, `_`, `:` and `-` starting with a letter.

The validator tests pass. The handler throws `NotImplementedException` and the integration test ends with `TODO(hardslice):`. A slice its module does not register fails the check too: a test of the host resolves every request handler and validator of the application from the container, and names the ones that are missing.

Without `--project`, before the first restore, with a name that is not PascalCase or ends with `Command`, for a module without `Features/<Module>/<Module>Module.cs`, with a `--response` DTO named `Guid` or as a type of the slice, with `--parameters none --response none`, with a `--route` that is not made of words and route parameters, or that names a parameter `id` with `--method DELETE`, with a method other than `POST`, `PUT`, `PATCH` and `DELETE`, `GET` included, with `--endpoint none` and `--route` or `--method`, with `--every` and an interval it does not accept, `--parameters id` or `--endpoint http`, with `--daily-at` and a time that is not `hh:mm`, `--every`, `--parameters id` or `--endpoint http`, with a `--time-zone` that is not an IANA id or without `--daily-at`, with a `--retry` that is not a delay and a count or without `--every` nor `--daily-at`, or with `--require` and `--endpoint none`, `--every`, `--daily-at` or a policy name it cannot write, it exits with an error that says what to do and creates nothing. It refuses to overwrite an existing slice without `--force`.

## A query slice

```text
dotnet new hardslice-query --project src/Rooms/Rooms.csproj --module Bookings --name GetBookingSummary --aggregate Booking
```

It creates `src/Rooms/Features/Bookings/GetBookingSummary/GetBookingSummary.cs`, with the query `GetBookingSummaryQuery`, its DTO `BookingSummaryDto`, its handler and its endpoint `GET /bookings/get-booking-summary/{id:guid}`, and the integration tests in `tests/Rooms.IntegrationTests/Features/Bookings/GetBookingSummary/`, then prints the lines to add to `BookingsModule.cs`. The handler reads `Set<Booking>()` with `AsNoTracking()` and projects it into the DTO with `Select`, so HS006 has nothing to report. By default it reads one DTO by its id, an unknown id being answered with 404. `--result many` reads the list instead. The DTO is named after the slice without its first word, the verb of the use case, for every result: `GetBookingSummary` returns `BookingSummaryDto`, `ListRoomBookings` `RoomBookingsDto`. A name of one word is kept whole, `Bookings` returning `BookingsDto`.

```text
dotnet new hardslice-query --project src/Rooms/Rooms.csproj --module Bookings --name GetBookingsOnDate --aggregate Booking --route bookings-on-date --result filtered --parameter Date:DateOnly
```

`--result filtered` reads the list that a filter selects. `--parameter <Name>:<Type>` names the filter, required with it and refused with the other results: a PascalCase name and one of `string`, `bool`, `int`, `long`, `decimal`, `double`, `Guid`, `DateOnly`, `TimeOnly` and `DateTimeOffset`, written as in C#. For another type, such as an enum of the domain, generate the query with the closest one, then change it. The query `GetBookingsOnDateQuery(DateOnly? Date)` returns the list of `BookingsOnDateDto`, and its endpoint binds it from the query string with `[AsParameters]`, such as `GET /bookings/bookings-on-date?date=2026-11-04`. The filter is nullable so that a request without it reaches the validator `GetBookingsOnDateValidator` (`NotNull()`, or `NotEmpty()` for a `string`), answered with 400 naming it. The template creates the unit tests of the validator in `tests/Rooms.Tests/Features/Bookings/GetBookingsOnDate/`, an integration test of the list that the filter selects and one of the 400 of a request without it, and prints the registration of the handler and of the validator. Its handler reads `Set<Booking>()` with `AsNoTracking()` and a `TODO(hardslice):` marker where the `Where` of the filter goes, with the joins of the other aggregates the use case reads. A second filter is a property of the query and a rule of its validator.

`--route` sets the route of the endpoint under the group of the module, as for a command: pass it every time, named after what the query reads, such as `--route summaries`, which maps `GET /bookings/summaries/{id:guid}`, the identifier of a single result following the route. `--route /` maps the group itself. `--method` accepts `GET` only: a query never changes state. `--require <policy>` protects the endpoint as for a command: `.RequireAuthorization("<policy>")`, an integration test of its 401 next to the test of the 404 or the 400, and the other tests through `app.CreateAuthorizedClient("<policy>")`. A route that is not made of words and route parameters, one that names a parameter `id` with a single result, any other method, `--result filtered` without `--parameter`, `--parameter` with another result, a filter that is not `<Name>:<Type>` of a listed type, and a policy name it cannot write are refused with an error, and nothing is created.

`--aggregate` is required: it names a type of the namespace `Rooms.Domain.Bookings` whose `Id` is an `<Aggregate>Id` that wraps a `Guid Value`, as `Booking` and `BookingId` do. An aggregate that does not exist fails the build with a compiler error that names it.

The handler works as generated: with one DTO by its id, the test of an unknown id passes, and with a filter, the validator tests and the test of the 400. The test that reads or lists a stored aggregate fails with `TODO(hardslice):` until it creates the aggregate through its factory method and asserts the values the DTO reads, and, with a filter, an aggregate that the filter excludes.

## A domain event and its reaction

```text
dotnet new hardslice-event --project src/Rooms/Rooms.csproj --module Bookings --name BookingExtended --reaction Payments/InvoiceOnBookingExtended
```

It creates the event `BookingExtended`, a `sealed record` that implements `IDomainEvent` with a `Guid Id` to replace by the values of the fact, in `src/Rooms.Domain/Bookings/Events/`. With `--reaction <Module>/<Slice>`, it also creates the reaction slice `src/Rooms/Features/Payments/InvoiceOnBookingExtended/`, whose only type is the `internal` handler `InvoiceOnBookingExtendedHandler`, an `IDomainEventHandler<BookingExtended>`, and its integration tests in `tests/Rooms.IntegrationTests/Features/Payments/InvoiceOnBookingExtended/`, then prints the usings and the registration to add to `PaymentsModule.cs`. The reaction may live in another module than the event: it depends on the domain only. It runs inside the transaction of the command that raised the event, so it changes aggregates and never calls an external service.

Without `--reaction`, it prints how to raise the event from the aggregate instead. With `--reaction-only` too, it creates the reaction slice alone, for an event that already exists, and leaves the event as it is. It never edits the aggregate: the method where the fact happens adds the event to its list.

The handler throws `NotImplementedException`, and its test, which calls it with an event as the pipeline does, then saves, ends with `TODO(hardslice):`. A reaction its module does not register fails the check twice: its test, and the test of the host, which also resolves every domain event handler. A name that HS019 does not read as a past fact, such as `ExtendBooking`, is created with a warning.

Without `--project`, before the first restore, with a name or a module that is not PascalCase, for a module without `Features/<Module>/<Module>Module.cs` (the module of the event or of the reaction), with a reaction that is not `<Module>/<Slice>` in PascalCase, ends with `Handler` or is named as the event, or with `--reaction-only` without `--reaction`, it exits with an error and creates nothing. It refuses to overwrite an existing event without `--force`.

## Limitations

- The item templates read the application and its modules through `--project` only, once the web project is restored: `dotnet new` evaluates no project from the root of a solution, and cannot read a file before it creates the others.
- A refusal prints `The template ... was created successfully.` before `Post action failed.` and its error, and exits with code 105: nothing is created.
- They only print the registrations of the module, of the slice or of the reaction, which you or the agent add to `Program.cs` or to the module. `hardslice-aggregate` and `hardslice-entity` print the migration to add, `hardslice-entity` the collection to add to the root, and `hardslice-event` how to raise the event.
- `hardslice-module` creates the contract of the module alone, as `dotnet new` creates no empty folder and never deletes a file: the templates of its aggregates, slices and events create its other folders. With `--force`, it overwrites the contract of an existing module, its registrations included.
- The tests that `hardslice-command` and `hardslice-query` generate call `<Module>Module.Route`, the constant that `hardslice-module` writes in the contract of the module. A module written by hand without it fails the build of these tests (CS0117): add `public const string Route` to it and map its group with it.
- They cannot check that the route of a slice is free in its module: two endpoints with the same method and route fail at run time, in the integration tests.
- `hardslice-entity` knows an aggregate by its mapping only, `Features/<Module>/<Aggregate>Configuration.cs`: it cannot tell a root from a child entity, nor read the root to add the collection to it.
- `hardslice-query` cannot check the aggregate: the compiler does. Its list result is `--result many`, not `list`, which `dotnet new` would read as its own `list` command. It generates one filter, of a listed type: add the others to the query. It cannot see the other slices of the module either: two queries whose names differ only by their verb, such as `GetBooking` and `FindBooking`, name the same DTO, which the module that registers both reads as ambiguous (CS0104) until one is renamed.
- `hardslice-event --reaction-only` cannot check that the event exists: the compiler does, and the test it generates leaves the building of the event to complete.
